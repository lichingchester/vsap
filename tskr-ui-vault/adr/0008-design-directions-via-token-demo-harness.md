# Site design is explored on a branch via a token-driven demo harness

The site's own visual design had grown by accident — a bare `bg-neutral-950 / text-neutral-100` Tailwind scaffold, which is exactly the generic palette that makes an AI-built frontend look generic. We want a **real, documented design system** (tokens in Tailwind v4 `@theme`), but a copy-paste *UI library* whose own site looks like every other AI SaaS undercuts its credibility, so the look has to be deliberate. Rather than design tokens up front, we **explore design directions on the `design-system` branch and let the demos earn the tokens**.

We decided:

- **A direction is a token set first; structural divergence is an explicit escape hatch.** The shared chrome (header, sidebar, snippet grid, snippet detail) hard-codes nothing visual — every colour, font, radius, space, shadow, and motion reads from a CSS variable, and a **design direction** is one filling of those variables, swapped via a `data-direction` attribute. Comparing directions and building the system are then the *same* activity. **But a token swap alone can make two directions feel like the same page recoloured.** When a direction needs to explore a genuinely different *structure* (not just colour), it may bring its own layout — the deliberate escape hatch. Direction B uses the shared shell; Direction C exercises the escape hatch (a sidebar-less gallery). Whatever wins still collapses to tokens plus, at most, one chosen layout.
- **Directions are judged on two real surfaces, not a swatch board.** Each direction renders the home page (hero + snippet grid) *and* a real snippet **detail** page (live preview + code tabs). The detail page carries the binding constraint that an ordinary marketing site doesn't have: **the chrome must recede so the snippet previews are the loud thing.** A direction can ace a hero and still drown a glowy preview; only the detail surface exposes that.
- **`/demos` is throwaway scaffolding.** When a direction wins, its tokens are promoted into the real `global.css @theme` and `Layout.astro`, and `/demos` is deleted before merge. The shipped site stays lean (project ethos).
- **The anti-slop gate is external and on-demand.** We install neither [impeccable](https://github.com/pbakaus/impeccable) nor [taste-skill](https://github.com/Leonxlnx/taste-skill) into the lean repo. We run `npx impeccable detect` against each demo *build* as an objective slop-gate, and borrow taste-skill's three dials (variance / motion / density) purely as vocabulary to spec a direction.

## Considered options

- **Restyle directly, no system.** Faster, but produces no reusable tokens and no honest way to compare alternatives — rejected because the Q1 deliverable is a documented system.
- **Adopt React Bits' look.** React Bits is the closest analog (a copy-paste animated-component collection) and the reference we like — but its identity is dark canvas + violet + purple-gradient + glow + Geist, which is both (a) derivative of a direct competitor and (b) the canonical "AI slop" palette the anti-slop tools exist to flag. We take its *UX* (dark canvas, generous spacing, restrained chrome, animated-gradient accent treatment) and reject its *identity* (see Direction B below).
- **Adopt a ready-made design system / the two reference repos as systems.** Rejected on a category error: impeccable and taste-skill are AI-guidance skills, not design systems — they ship no tokens, type, or components.

## Consequences

- **Direction B** — warm amber/gold accent (`#F5B544`) on a neutral charcoal canvas (`#0E0E11`), tight radii, a non-Inter/non-Geist type pairing — a deliberate 180° from React Bits' cool violet, chosen so the cool, glowy snippet previews pop against warm chrome. Uses the shared shell: full-width header + left snippet sidebar + contained main.
- **Direction C** — a structurally different exploration (escape hatch): no sidebar, a top category-filter bar, and an edge-to-edge bento gallery where live preview tiles are the navigation; dark, technical, hot-magenta accent, monospace headings. Added because the first C attempt (a recolour of B's shell) felt like "B with different colours."
- The demos are populated by a throwaway placeholder **catalog** (`src/components/demos/catalog.ts`) — the two real snippets plus ~23 placeholders — so the sidebar, grid, and gallery show what a *full* tskr/ui looks like rather than two lonely cards.
- **Direction D** — the synthesis after first review. Two things are **confirmed** and no longer in play: the main colour is B's **amber `#F5B544`**, and the detail page carries **live props controls** (colours / direction / speed drive the preview in place, echoing the flagship playground of ADR-0007). D reuses B's tokens on the shared sidebar shell.
- **Direction E** — refines the sidebar rule: the sidebar is **not** global. The **home page is a no-sidebar marketing landing** (own structure: hero + product-shot stage + featured strip + value band + CTA), while the **detail page keeps the sidebar shell + props controls** (`/demos/e/detail`). This is the landing → docs-app split; the earlier "sidebar always" from the D round was corrected here. E carries the confirmed amber.
- B, C, D, E accumulate rather than replace: each new direction is added without rewriting the prior ones, so the harness shows the full exploration trail.
- **Homepage — confirmed: Terminal · Masthead.** After a homepage round (Centered / Bento / Split / Terminal, then three Terminal treatments) the chosen home is a monospace, dev-tool landing with **no sidebar**: wordmark, tagline, CTA buttons, a mono stats row, "Why tskr/ui" as `#` comment lines, then a typographic index of every snippet.
- **Detail page — confirmed: stacked docs layout with the Panel props controls.** A three-column docs page (modelled on shadcn + React Bits) that **keeps the left sidebar** (snippet **name only**, monospace), a breadcrumb with the snippet name in accent, **no prose description**, and sections **Preview → Props → API → Usage** with a right-hand "On this page" TOC. The props-control field style is **Panel** (a bordered control panel), chosen over Inline and the merged interactive Table; a props **API table** (Prop / Type / Default / Description) documents every prop. Props schema lives in `gradientProps.ts` for the demo and would move into each snippet's `meta.ts` on promotion.
- **Confirmed tokens:** main colour **amber `#F5B544`** on charcoal `#0E0E11`; type **Bricolage Grotesque** (display) / **Hanken Grotesk** (UI) / **JetBrains Mono** (code, and the terminal wordmark/index); tight radii (4/6/8); `--text-muted` / `--text-dim` raised for WCAG AA on the dark canvas. The sidebar is contextual: **none on the home, present on detail pages.**
- **Promotion deferred.** The design is confirmed but **not yet promoted**: `/demos` and the `data-direction` mechanism remain in place. Remaining design details (and the eventual promotion of the winning tokens + the two layouts into the real `@theme` / `Layout.astro`, plus deleting `/demos`) are to be explored in a later session, continuing the same `/demos` pattern.
- The site temporarily carries a `/demos` route and a `data-direction` token mechanism that exist only to choose a design; both disappear on promotion.
- Whichever direction wins is adopted by *promotion of its token set*, not a redesign — the demos are the design system in embryo.
